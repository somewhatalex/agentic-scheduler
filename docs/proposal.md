# Step-Level Remaining-Work Prediction for Scheduling LLM Agents

## Motivation
Scheduling Agentic AI tasks is difficult because execution length is unknown in advance. Agents can invoke subagents, make tool calls, and retry multiple times. Thus, different tasks can vary in time by orders of magnitude, so when agents share the same compute cluster, scheduling becomes an important method to reduce waiting times.

## Related Work
Traditional LLM serving systems schedule requests first-come, first-served (FCFS), so short requests can get trapped behind longer ones. SSJF [1] approximates the time to completion and schedules shorter tasks first. A lightweight proxy model predicts each request’s output length from its prompt, and SSJF successfully reduces average completion time compared to a FCFS scheduler. However, SSJF estimates only from the initial prompt and does not update its estimate as execution progresses. An alternative system, Agentix [2], models an agentic program as a dynamic DAG of LLM calls, interleaved with external interrupts such as human input, tool calls, and code execution. It prioritizes each LLM call by the total service its program has already received, so it deprioritizes long-running programs and lets short programs finish first. Unlike our approach, Agentix does not predict remaining work, instead prioritizing agents based on already completed work.

Both systems leave a gap for tool-using agents: SSJF predicts once per request from the prompt, without accounting for tool calls or tool latency, and Agentix does not estimate remaining work. We fill this gap with a step-level remaining-work predictor for agent trajectories that re-predicts after every step.

## Idea Outline
We propose a scheduler that prioritizes ready agent tasks by their predicted remaining execution time, updating estimates after each completed step. Agents waiting on external tool calls release the LLM server until their tools return. The input is the list of pending tasks, each described using the original prompt plus the sequence of steps completed so far (LLM turns, tool calls, and their token counts), and the output is the corresponding remaining-work predictions for the tasks. We will predict the remaining length and repredict after every step rather than only from the initial prompt.
Dataset
We plan to use NVIDIA’s Nemotron-SFT-Agentic-v2 dataset as our primary dataset. This dataset contains 991,900 synthetic LLM agent trajectories across a wide range of tool-using scenarios. NVIDIA splits up the dataset into 3 overarching categories: 707,052 general tool-calling trajectories, 278,880 customer service trajectories, and 5,968 search trajectories. These trajectories cover both single- and multi-step tasks and include diverse tool-use scenarios drawn from sources such as API-Bank and Toucan-1.5M [3].

The Nemotron dataset is a good fit for our prediction task because it concisely breaks down agent trajectories into sequences of distinct steps and tool calls, with associated metadata such as the number of tokens [3]. This dataset structure allows us to truncate a completed trajectory at an intermediate point as input into the prediction model. The remaining portion of the trajectory can then serve as the ground-truth outcome against which the model’s prediction is evaluated. We will split complete trajectories into training and test sets before generating intermediate examples to prevent data leakage. One limitation is the lack of a dedicated software-development workload, which may have substantially different planning, execution, and testing behavior. Thus, it may be beneficial to introduce software development agent trajectories to supplement the Nemotron dataset. The SWE-smith dataset is a promising candidate and contains 26k trajectories based on tasks sourced from 128 GitHub repositories, and uses a similar step-based structure as Nemotron [4].

## Method
For the sake of this task, our goal is to reduce the average amount of time a user would have to wait for a given agentic trajectory call to finish. As mentioned before, we could naively order on a first-come, first-served basis, but this can push simple short calls to be after very long ones. We aim to not only be able to reorder agentic calls based on when they start, but also to reevaluate their priority while they execute. We will be looking at this as a continuous prediction task in two dimensions. First, the number of remaining tool calls, and secondly, the remaining agent execution time. The first is a simpler evaluation that can be tested on a larger scale, but due to variation in tool call time, the second is also necessary.

Similar to the SSJF paper, we will formulate two regression tasks. Both will take as input the user request and all information generated so far, if any. The first will predict the remaining number of tool calls, and the second will predict the remaining agent execution time. We use the predicted remaining execution time to prioritize agents, while evaluating remaining tool calls as a simpler prediction task.

We train the regression models to predict log(1+y) for each target, using Huber loss to reduce sensitivity to unusually long trajectories and large prediction errors. The input has two parts: the user request (truncated to BERT’s 512-token limit) and a numeric summary of progress so far, namely the step index, cumulative and last-turn token counts, tool calls so far, the last tool name, the tool output size, and a repeated-call flag. We compare three predictors: a step-conditional mean baseline, gradient-boosted trees trained on progress features, and a fine-tuned BERT model incorporating the original request and execution history. If time permits, we will also evaluate a ~1B parameter LLM fine-tuned using LoRA and a regression head. We re-predict after every completed step. We will also evaluate the computational overhead of re-prediction to determine whether it outweighs the scheduling benefits for each predictor. Because Nemotron has no timing fields, we estimate remaining execution time using profiled LLM inference speeds and per-tool latencies sampled from measured agent traces. To test transfer to workloads the model has not seen, we hold out whole domains (the customer-service subset spans 838 domains, each tagged with a domain field) and entire subsets (train on tool-calling and customer service, search test, and test zero-shot on SWE-smith). We use workload-agnostic progress features, and fall back to prioritizing by attained service, as Agentix does, when little history exists. We also report, for each workload, how strongly the number of steps completed correlates with the number remaining. This tells us when remaining-work prediction should help over attained service, and when it should not.

## Evaluation Metrics
The system will be evaluated at both the prediction and scheduling levels using held-out test data. We will evaluate remaining tool calls and time predictions using MAE and MSE on the log scale, and Kendall’s τ to measure agreement between predicted and actual remaining-work rankings. Metrics will be reported by step and held-out domain. For scheduling, we will run sets of n randomly selected test tasks and measure average task completion time, averaging results across sets. We will apply the same evaluation to baseline schedulers such as SSJF and Agentix to quantify the efficiency improvement of our approach.
